# 账号管理与帐号资料合并开发方案

## 1. 文档目的

本文档用于指导 Zephyr Hub 将现有“账号管理”和“帐号资料”整合为统一的账号生命周期管理功能。

整合后的系统需要回答三个核心问题：

1. 账号从哪里获得，目前有哪些基础资料。
2. 账号凭据是否已经准备完成、是否仍然有效。
3. 账号部署到了哪个 CPA 或 Sub2API，当前是否可以正常调度。

本方案不是简单地将两个页面放入同一组 Tab，而是建立本地账号资料、加密凭据和上游部署资源之间的持久关联。

## 2. 当前实现

### 2.1 帐号资料

当前帐号资料由 `account_vault_entries` 保存，主要包含：

- 邮箱和显示名称。
- 加密登录密码。
- 账号业务状态。
- 购买日期和质保信息。
- 备注和来源指纹。
- 接码手机号及验证码查询关系。

相关实现：

- `app/pages/admin/account-vault.vue`
- `server/api/admin/account-vault/`
- `server/services/accounting.ts`
- `server/services/sms-receivers.ts`

### 2.2 账号管理

当前账号管理直接操作外部系统中的资源：

- CPA 认证 JSON 文件。
- Sub2API 账号。
- Sub2API 分组。
- Sub2API 代理。
- 上游操作记录。

相关实现：

- `app/pages/admin/upstreams.vue`
- `server/api/admin/upstreams/`
- `server/services/cpa.ts`
- `server/services/sub2api-admin.ts`
- `server/services/upstream-operations.ts`

### 2.3 当前缺口

两套功能之间目前没有账号级关联：

- 无法判断一条帐号资料是否已经部署。
- 无法判断账号部署到了 CPA、Sub2API，还是两者都有。
- 无法从本地账号直接查看上游分组、代理和调度状态。
- 删除上游资源后，本地账号资料无法感知。
- 直接导入到上游的账号不会自动进入帐号资料库。
- 操作记录只能看到上游资源，无法追溯到本地账号主体。

因此，仅合并菜单或页面不能解决核心问题。

## 3. 产品结构

### 3.1 导航和路由

管理员侧只保留一个一级菜单：

```text
账号管理
```

建议主路由：

```text
/admin/accounts
```

旧地址保留兼容跳转：

```text
/admin/account-vault -> /admin/accounts
/admin/upstreams     -> /admin/accounts
```

### 3.2 主页面

主页面使用一张统一账号表，不使用“帐号资料”和“上游账号”两个主 Tab。

每一行代表一个实际账号，建议列如下：

| 列 | 内容 |
| --- | --- |
| 账号 | 邮箱、名称、平台、账号标识 |
| 来源与质保 | 来源、购买日期、质保截止日期 |
| 凭据 | 未准备、有效、即将过期、失效 |
| CPA | 未部署、运行、停用、异常 |
| Sub2API | 部署状态、分组、代理、调度状态 |
| 接码 | 绑定手机号、最新验证码状态 |
| 最近验证 | 最近一次验活时间和结果 |
| 操作 | 查看、编辑、部署、验活、更多操作 |

页面顶部提供：

- 搜索。
- 平台筛选。
- 资料状态筛选。
- 凭据状态筛选。
- 部署目标筛选。
- 部署状态筛选。
- 添加账号。
- 批量导入。
- 资源配置。

### 3.3 账号详情抽屉

点击账号后打开右侧详情抽屉，内容顺序如下：

1. 基础资料。
2. 密码与接码信息。
3. 凭据版本。
4. CPA 部署。
5. Sub2API 部署。
6. 额度和验活结果。
7. 账号相关操作记录。

抽屉顶部优先显示用户真正需要查看的文本状态，详细 JSON 放在对应信息之后。

### 3.4 资源配置

Sub2API 分组和代理不是账号主体，不放入账号主表。

在账号管理页面提供“资源配置”按钮，打开独立管理抽屉或全屏弹窗，包含：

- Sub2API 分组。
- Sub2API 代理。
- 新账号默认代理。
- CPA/Sub2API 连接状态。
- 全局上游操作记录。

单个账号的分组和代理仍在账号详情或部署向导中配置。

## 4. 账号生命周期

统一后的账号生命周期如下：

```text
获得账号
  -> 建立账号资料
  -> 绑定接码手机号
  -> 上传或生成凭据
  -> 部署到 CPA/Sub2API
  -> 主动验活
  -> 进入调度
  -> 监控额度和异常
  -> 更新凭据或停止部署
```

资料状态、凭据状态和部署状态必须分别保存，不能复用同一个 `status` 字段。

### 4.1 资料状态

```text
active
disabled
expired
banned
sms_invalid
```

现有中文业务状态可以保留为展示标签，但服务层应使用稳定的内部枚举。

### 4.2 凭据状态

```text
missing
ready
expiring
expired
invalid
revoked
```

### 4.3 部署状态

```text
pending
active
inactive
unschedulable
error
removed
reconciliation_required
```

## 5. 部署向导

账号行和详情抽屉提供“部署”操作。

部署流程：

```text
选择账号
  -> 准备凭据
  -> 选择部署目标
  -> 配置目标参数
  -> 预览
  -> 导入
  -> 主动验活
  -> 保存部署关系
```

### 5.1 凭据来源

支持以下来源：

1. 上传已有 JSON。
2. 使用账号已有的加密凭据版本。
3. 使用 GPTSession 转换功能生成 CPA/Sub2API 凭据。
4. 从 Sub2API 官方导出包解析多个账号。

### 5.2 部署目标

支持：

- 仅 CPA。
- 仅 Sub2API。
- 同时部署到 CPA 和 Sub2API。

### 5.3 CPA 配置

- 认证文件名称。
- 是否立即启用。
- 导入后主动验证。

### 5.4 Sub2API 配置

- 分组。
- 代理。
- 并发数。
- 优先级。
- 倍率。
- 是否允许调度。
- 导入后主动验活。

默认值优先级：

```text
用户本次选择
  > 凭据或导出包中的关联
  > 账号上一次部署配置
  > 系统默认配置
```

## 6. 数据模型

### 6.1 账号主记录

短期可以继续使用 `account_vault_entries` 作为账号主记录，避免一次性迁移所有帐号资料和接码绑定。

建议增加：

```text
platform
canonical_identity
identity_type
record_status
credential_status
last_verified_at
last_verification_error
```

直接导入的 OAuth 或 Service Account 可能没有登录密码，因此：

- `encrypted_password` 应允许为空。
- 邮箱不能作为所有平台的唯一必填身份。
- `canonical_identity` 用于保存邮箱、OpenAI Account ID 或平台账号 ID。

### 6.2 凭据版本表

新增 `account_credentials`：

```text
id
account_id
credential_type
encrypted_payload
payload_fingerprint
source
status
expires_at
last_used_at
created_by
created_at
updated_at
```

说明：

- 同一账号允许存在多个凭据版本。
- 每次部署记录实际使用的凭据版本。
- 明文凭据不进入普通列表 API、日志或审计详情。
- `payload_fingerprint` 用于去重，不用于还原凭据。

### 6.3 部署关系表

新增 `account_deployments`：

```text
id
account_id
credential_id
connection_id
target_type
upstream_resource_id
status
schedulable
group_ids
proxy_id
settings_snapshot
last_verified_at
last_error
created_by
created_at
updated_at
removed_at
```

字段说明：

- `connection_id` 当前为 `cpa` 或 `sub2api`，为以后支持多个实例预留。
- `upstream_resource_id` 保存 Hub 可解析的上游资源引用。
- `settings_snapshot` 记录部署时的非敏感配置。
- 删除上游资源时将部署状态更新为 `removed`，不删除账号主记录。

### 6.4 操作记录关联

给 `upstream_control_operations` 增加可空字段：

```text
account_id
deployment_id
```

这样可以从账号详情直接查询该账号的导入、验活、启停和删除记录。

## 7. 账号匹配与去重

账号匹配优先级：

```text
平台账号 ID 完全一致
  > 标准化邮箱完全一致
  > 已知凭据身份指纹一致
  > 管理员手动关联
```

禁止行为：

- 不按照显示名称自动合并。
- 不按照备注自动合并。
- 多个本地账号匹配同一个上游资源时，不自动选择。
- 不因为匹配失败而删除或重新导入上游资源。

冲突记录进入“待确认”状态，由管理员处理。

## 8. 现有数据迁移

### 8.1 迁移原则

- 先增加新表和可空字段。
- 不修改现有账号密码密文。
- 不修改接码绑定。
- 不对 CPA/Sub2API 执行写操作。
- 首次对账只读取上游数据。

### 8.2 首次对账

1. 读取全部本地帐号资料。
2. 读取 CPA 认证文件列表。
3. 读取 Sub2API 账号列表。
4. 提取标准化邮箱、平台账号 ID 和凭据指纹。
5. 对唯一且高置信度的结果自动建立部署关系。
6. 将冲突资源标记为“待确认”。
7. 将没有本地资料的上游资源标记为“待认领”。

### 8.3 待认领资源

管理员可以：

- 关联到已有账号。
- 创建新的账号主记录。
- 标记为外部托管，不进入本地密码管理。
- 忽略该资源。

## 9. 删除和更新规则

### 9.1 删除账号资料

存在活动部署时禁止直接永久删除账号主记录。

管理员必须先选择：

- 仅停止调度。
- 从 CPA/Sub2API 删除部署。
- 保留上游资源并解除本地关联。

### 9.2 删除上游资源

删除 CPA/Sub2API 资源后：

- 账号资料继续保留。
- 对应部署记录更新为 `removed`。
- 操作记录继续保留。
- 可以使用已有凭据重新部署。

### 9.3 更新凭据

- 创建新凭据版本，不覆盖旧版本密文。
- 新部署默认使用最新有效版本。
- 已部署资源是否同步更新由管理员确认。
- 旧版本在确认无引用后才能撤销或删除。

## 10. 权限和安全

统一页面不能降低原帐号资料页面的权限要求。

### 10.1 角色权限

| 角色 | 资料 | 密码 | 凭据 | 部署 | 审计 |
| --- | --- | --- | --- | --- | --- |
| super_admin | 完整 | 查看/复制 | 管理/部署/导出 | 完整 | 完整 |
| admin | 完整 | 查看/复制 | 管理/部署 | 完整 | 完整 |
| operator | 脱敏 | 不可查看 | 不可导出 | 验活、启停、部署 | 相关记录 |
| auditor | 只读脱敏 | 不可查看 | 不可查看 | 只读 | 完整 |
| user | 无权限 | 无权限 | 无权限 | 无权限 | 无权限 |

### 10.2 凭据保护

- 使用现有 `NUXT_ENCRYPTION_KEY` 进行带上下文的 AEAD 加密。
- 账号密码、OAuth Token、Refresh Token 和代理密码使用不同加密上下文。
- 列表 API 不返回明文凭据。
- 凭据部署在服务端完成，不经过浏览器二次回传。
- 导出凭据需要管理员重新认证。
- 审计日志只记录指纹、版本 ID、目标和结果。
- 请求错误必须经过敏感字段脱敏。
- 不在 Redis 中长期保存明文凭据。

## 11. API 规划

建议新增统一 API：

```text
GET    /api/admin/accounts
POST   /api/admin/accounts
GET    /api/admin/accounts/:id
PATCH  /api/admin/accounts/:id
DELETE /api/admin/accounts/:id

GET    /api/admin/accounts/:id/credentials
POST   /api/admin/accounts/:id/credentials
DELETE /api/admin/accounts/:id/credentials/:credentialId

GET    /api/admin/accounts/:id/deployments
POST   /api/admin/accounts/:id/deployments
POST   /api/admin/accounts/:id/deployments/:deploymentId/verify
PATCH  /api/admin/accounts/:id/deployments/:deploymentId
DELETE /api/admin/accounts/:id/deployments/:deploymentId

GET    /api/admin/accounts/unclaimed
POST   /api/admin/accounts/unclaimed/:resourceId/claim
POST   /api/admin/accounts/reconcile
```

现有 CPA/Sub2API 管理 API 暂时保留，由统一 API 的部署服务复用，避免同时重写上游适配层。

## 12. 服务层边界

建议新增：

```text
server/services/account-lifecycle.ts
server/services/account-credentials.ts
server/services/account-deployments.ts
server/services/account-reconciliation.ts
```

职责：

- `account-lifecycle.ts`：账号主记录和综合视图。
- `account-credentials.ts`：凭据版本、加密、到期和撤销。
- `account-deployments.ts`：部署编排、验活、启停和删除。
- `account-reconciliation.ts`：本地账号与上游资源匹配。

现有 `cpa.ts` 和 `sub2api-admin.ts` 继续只负责外部系统协议，不直接管理本地账号生命周期。

## 13. 实施阶段

### 第一阶段：数据关联

- 新增凭据表和部署关系表。
- 扩展账号主记录。
- 给上游操作增加账号关联。
- 实现只读对账和待认领资源。
- 为现有接口补充账号关联参数。

### 第二阶段：统一页面

- 新增 `/admin/accounts`。
- 建立统一账号表。
- 实现账号详情抽屉。
- 实现资源配置抽屉。
- 将旧页面改为兼容跳转。

### 第三阶段：部署闭环

- 实现单账号部署向导。
- 实现批量部署。
- 接入 GPTSession 转换。
- 部署后自动验活并保存关联。
- 增加重新部署和凭据更新流程。

### 第四阶段：运营能力

- 凭据到期提醒。
- 账号质保到期提醒。
- 上游异常与本地账号联动。
- 账号额度和部署健康汇总。
- 批量停用、迁移分组和更换代理。

## 14. 测试要求

### 14.1 单元测试

- 账号匹配和冲突检测。
- 凭据加密、解密和上下文隔离。
- 部署状态转换。
- 删除保护。
- 权限矩阵。
- 敏感字段脱敏。

### 14.2 契约测试

- CPA 上传、验活、启停和删除。
- Sub2API 导入、分组、代理、调度和验活。
- 部署成功后本地关系写入。
- 上游成功但本地写入失败时进入待对账状态。
- 幂等键防止重复部署。

### 14.3 页面测试

- 桌面和移动端统一账号表。
- 详情抽屉。
- 部署向导。
- 待认领资源。
- 批量导入和批量部署。
- 长邮箱、长备注和上游错误信息不破坏布局。

## 15. 验收标准

完成后应满足：

1. 管理侧只有一个“账号管理”一级菜单。
2. 每个账号都能看到资料、凭据、CPA 部署和 Sub2API 部署。
3. 可以从账号行直接发起 CPA/Sub2API 部署。
4. 部署成功后自动建立本地关联并主动验活。
5. Sub2API 分组和代理可以在部署时选择。
6. 已部署账号不能被误删本地资料。
7. 直接存在于上游的账号可以被认领或关联。
8. 密码和 OAuth 凭据不会出现在普通列表、日志和审计正文中。
9. CPA/Sub2API 写操作均有幂等保护和待对账处理。
10. 旧页面地址可以安全跳转到统一页面。

## 16. 推荐结论

推荐采用“一个账号主体、多个凭据版本、多个部署关系”的结构。

主页面围绕账号主体组织，不再区分“帐号资料页面”和“上游账号页面”；CPA、Sub2API、分组和代理作为账号部署能力存在。这样既符合实际业务流程，也能避免资料、凭据和上游状态继续分散。
